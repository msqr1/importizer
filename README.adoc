= importizer
:toc: preamble
:hide-uri-scheme:

Are you looking to convert your header-based C{plus}{plus} codebase to C{plus}{plus}20 modules, but
afraid that modularizing is too cumbersome? *importizer* is here to help.

This project uses https://semver.org[semantic versioning].

*Note:* This project is currently going through a complete rewrite using LibTooling to replace
Regex (pre-2.0.0).
Much pre-2.0.0 code are gone, but releases and git history are preserved.

== Why C{plus}{plus} modules?
* *Improved encapsulation:* Modules allow you to choose what is exposed to users (exported), no need
to hide stuff with a `detail` namespace.
Includes and macros from a module will only stay in that module.
* https://arewemodulesyet.org

=== Native modules
Native modules mean using modules internally.
Some advantages of native modules are:

* *Improved compilation time:* Modules don’t need to be recompiled every time it is imported, unlike
headers.
* *No ordering issues:* Modules are compiled in a topological order, and `import`s can be ordered
freely.

=== Wrapped modules
Wrapped modules mean exposing a modules interface by wrapping the underlying headers.
Some advantages of wrapping modules are:

* *Support modules with headers:* Support a growing amount modules user while not breaking headers.

Required shared libraries, if applicable, are bundled within the distribution.

== Configuration and usage
Importizer primarily uses a YAML configuration file, along a few command-line options.

=== Command-line interface (CLI)
By default, running `importizer` looks for an `importizer.yml` file in the current working
directory.
You can override this by passing the path as a positional argument: `importizer
path/to/configuration.yml`.

[%autowidth]
|===
|Option |Description

|-h, --help
|Display available options.

|--help-list
|Display list of available options.

|--version
|Display version.

|-w, --write
|Actually rewrite files.
Without this flag importizer does everything else but that.
It's useful for validating configuration, see if your project is modularizable, and see a summary of
what will change.
|===

=== Configuration file (YAML)
Relative paths in the configuration file are resolved relative to the file’s location, *not* the
current working directory.
For globs, it's always:

* First match wins.
* Prefixing patterns with `!` negates them.
* See https://llvm.org/doxygen/classllvm_1_1GlobPattern.html[here] for more info.

[%autowidth]
|===
|Option |Type |Description

|root
|string
|*Required.* Root of the project to run importizer on.
Globs are resolved through this.

|hdrGlobs
|string array
|*Required.* Glob patterns to match header files to be modularized.

|compilationDB
|string
|Path to a `compile_commands.json` compilation database to provide context.

|explicit
|object
|See the <<explicit-mode, Explicit mode>> section.

|stdImport
|boolean
|Replace C{plus}{plus} headers inclusion with `import std;` and if C wrappers headers are used,
`std.compat`.
|===

==== Explicit mode
importizer supports projects without a JSON compilation database via the `explicit` object.
This can be the case for projects using a build system without JSON compilation database generation.
`explicit` is mutually exclusive with `compilationDB` but at least one of them must be specified.

[%autowidth]
|===
|Option |Type |Description

|srcGlobs
|string array
|*Required.* Glob patterns to match source files to be modularized.

|compileFlags
|string array
|Compile flags for source files.
Defaults to `[]`.
|===

=== Example configuration file
[,yml]
----
root: .
hdrGlobs:
  - src/**.hh
# compilationDB: build/compile_commands.json
explicit:
  srcGlobs:
    - src/**.cc
  compileFlags:
    - -I3rd-party/clang/include
    - -I3rd-party/llvm/include
    - -I3rd-party/doctest/include
----
